== 🎯 Objective

The goal is to keep execution *simple and lightweight*:

* Users do *not* need to clone the repository manually
* Only required files (wrappers + config) are downloaded
* Wrapper scripts handle cloning and execution internally

== 📋 Prerequisites

Before running either script, ensure the following are in place:

. *AWS CLI* is configured and logged in to the correct AWS account
. *Bash* is available (Linux or macOS)
. *Internet access* is available for cloning repos and downloading packages
. Ensure you have access to the target AWS account where resources will be created

NOTE: The scripts automatically install `git`, `terraform`, `python3`, `ansible-core`, and required network tools (`wget`, `telnet`, `net-tools`, `bind-utils`, etc.). No pre-installation is needed.

== ⚙️ Configuration

[[operator-editing-checklist]]
=== Operator editing checklist

These are *wrapper inputs*, not a dotenv file for Ansible or native Terraform
tfvars. From the download directory, select one file explicitly:

[source,bash]
----
vi .tfvars.yaml
export TFVARS_FILE="$PWD/.tfvars.yaml"
# Shell alternative (do not edit the loader at the bottom):
# vi .tfvars.env
# export TFVARS_FILE="$PWD/.tfvars.env"
----

In `vi`, press `i`, edit, then `Esc`, `:wq`, Enter to save/quit;
`Esc`, `:q!`, Enter quits without saving. `.tfvars.env` is executable shell
configuration: use only trusted files. YAML keys are lowercase; shell keys
are uppercase. Check every applicable row before provisioning:

[cols="2,3,3", options="header"]
|===
| Requirement | YAML keys | Shell keys / action

| Always verify account, region, ownership
| `aws_region`, `owner`, `environment`
| `AWS_REGION`, `OWNER`, `ENVIRONMENT`; select the intended `AWS_PROFILE` externally. Environment also selects the Terraform workspace.

| Always choose resource modes
| `create_vpc`, `create_new_sg`, `create_keypair`, `create_eip`
| `CREATE_VPC`, `CREATE_NEW_SG`, `CREATE_KEYPAIR`, `CREATE_EIP`; `create_vpc: false` means the account's *default* VPC, not an arbitrary VPC ID.

| Existing SG / key pair (conditional)
| `existing_sg_name`, `existing_keypair_name`
| `EXISTING_SG_NAME` (SG ID or name in the target VPC), `EXISTING_KEYPAIR_NAME` when corresponding create flags are false. Verify actual resources, not default example names; an existing key pair also requires its matching private key for Ansible.

| New VPC (conditional)
| `vpc_name`, `vpc_cidr_block`, `vpc_azs`, `vpc_public_subnets_cidr`, `vpc_private_subnets_cidr`, `enable_nat_gateway`, `enable_vpn_gateway`
| `VPC_NAME`, `VPC_CIDR_BLOCK`, `VPC_AZS`, `VPC_PUBLIC_SUBNETS_CIDR`, `VPC_PRIVATE_SUBNETS_CIDR`, `ENABLE_NAT_GATEWAY`, `ENABLE_VPN_GATEWAY`; match AZs to the selected region and review overlapping CIDRs.

| New SG (conditional)
| `sg_name` or `sg_name_suffix`, `allow_all`, `allowed_cidrs`
| `SG_NAME` / `SG_NAME_SUFFIX`, `ALLOW_ALL`, `ALLOWED_CIDRS`; use your approved controller/client CIDRs, not the shipped addresses. Keep `allow_all` false. The module allows *all traffic* from allowed CIDRs; `allowed_ports` / `ALLOWED_PORTS` is deprecated and *ignored*, not a port restriction.

| New key pair / EIP (conditional)
| `keypair_name` or `keypair_name_suffix`, `cldr_eip_name`
| `KEYPAIR_NAME` / `KEYPAIR_NAME_SUFFIX`, `CLDR_EIP_NAME`; verify naming and avoid accidental collisions.

| Always verify image and capacity
| `ami_id`; `instance_groups` entries `cldr_mngr`, `ipa_server`, `pvcbase_master`, `pvcbase_worker`, `pvcecs_master`, `pvcecs_worker`, each with `count`, `instance_type`, `volume_size`
| `AMI_ID`; prefixes `CLDR_MNGR`, `IPA_SERVER`, `PVCBASE_MASTER`, `PVCBASE_WORKER`, `PVCECS_MASTER`, `PVCECS_WORKER`, each with `_COUNT`, `_INSTANCE_TYPE`, `_VOLUME_SIZE`. Verify region, OS, architecture, quota and disk requirements; example AMIs/sizing are not portable. For AD without FreeIPA set IPA count to zero; base-only deployments set both ECS counts to zero.

| Optional architecture / tooling
| `cpu_architecture`, `apply_graviton_defaults`, `auto_resolve_arm64_ami`, `ecs_deploy_on_arm64`, `terraform_version`
| `CPU_ARCHITECTURE`, `APPLY_GRAVITON_DEFAULTS`, `AUTO_RESOLVE_ARM64_AMI`, `ECS_DEPLOY_ON_ARM64`, `TERRAFORM_VERSION`; ARM64 ECS is experimental and off by default.
|===

`cm_version` / `CM_VERSION` here is a wrapper reference, not an Ansible
deployment override. Set product versions, domain, identity and service choices
using `vi config.yml` from `cdp-onprem-automation/ansible-playbooks/` and the
link:ansible-playbooks/docs/CONFIGURATION.md#operator-editing-checklist[Ansible checklist].
If configuring a pre-cloned checkout, use `pvc_setup.sh` there after editing;
clone wrappers fetch/checkout/pull the selected branch and may conflict with
local tracked edits. Do not rely on edits surviving a checkout refresh.

Validate in order: check syntax locally (`bash -n .tfvars.env` for the shell
format), confirm the AWS identity, then review a plan before any apply:

[source,bash]
----
aws sts get-caller-identity
DRY_RUN=true SHOW_TF_PLAN_OUTPUT=true ./clone_and_run_terraform.sh
----

The wrapper dry run does *not* apply infrastructure or copy inventory, but can
install tools, update the checkout, initialize Terraform, select/create a local
workspace and reconcile state. It is not an offline/no-write validator.
Protect plan/state/log files; plans can contain sensitive data. Only after plan
review run the normal provisioning command, then review generated inventory
without editing it and complete the Ansible checks before deployment.

=== Standalone AWS Terraform (without wrappers)

From the repository root:

[source,bash]
----
cd terraform-code/cloudera-pvc-terraform
vi terraform.tfvars
terraform init
terraform validate
terraform plan
----

This file is *HCL*, not shell/YAML; the root module does not read `.tfvars.yaml`
or `.tfvars.env` itself. Review `aws_region`, `pvc_cluster_tags`, `vpc_tags`,
`create_vpc`, `vpc_name`, `vpc_cidr_block`, `azs`, `public_subnets_cidr`,
`private_subnets_cidr`, `enable_nat_gateway`, `enable_vpn_gateway`,
`create_new_sg`, `sg_name`, `existing_sg`, `allow_all`, `allowed_cidrs`,
`create_keypair`, `keypair_name`, `existing_keypair_name`, `create_eip`,
`cldr_eip_name`, and `ipaserver_ec2_startstop_iam_enabled`.
`keypair_name` and `cldr_eip_name` have no defaults in `variables.tf`.
For every `instance_groups` entry review `count`, `ami`, `instance_type`,
`volume_size`, `tags`, and optional `user_data`. The checked-in HCL sample uses
small example instances and permissive ingress: replace these, especially
`allow_all` / `allowed_cidrs`, before a plan.

Do not edit `modules/*/terraform.tfvars` for a root-module run; Terraform does
not automatically load child-module tfvars. `init` downloads dependencies and
initializes the backend; `validate` checks configuration; `plan` queries AWS
but does not apply changes. Neither replaces account/network/size review.
Keep the same backend/workspace when switching entry points to avoid managing
the same resources in independent states.

Never edit generated `ansible_inventory.ini`, AWS-generated `inventory.ini`,
`terraform_output.json`, `tfplan.out`, `.terraform/`, or Terraform state.
Correct source inputs and regenerate inventory from the intended state.
Ansible-only inventories copied from the template are operator-owned instead.

== ▶️ How to run it ????

=== Step 1 — Update Configuration File

Edit `.tfvars.env` or `.tfvars.yaml` (use one, not both):

[source,bash]
----
vi .tfvars.env
# or
vi .tfvars.yaml
----

Update:

* AWS region
* Environment name
* CDP version
* Owner
* Instance configuration (if needed)

[source,bash]
----
#!/bin/bash

AWS_REGION="ap-southeast-1"
OWNER="ksahu-ygulati"
ENVIRONMENT="development"
TERRAFORM_VERSION="latest"
CM_VERSION="7.13.2.6"
----

NOTE: No need to modify Terraform or Ansible code.

=== Step 2 — Provision Infrastructure

[source,bash]
----
./clone_and_run_terraform.sh
----

This will:

* Clone Terraform automation (or pull latest changes)
* Create AWS infrastructure:
** VPC, subnets, security groups
** Key pairs and Elastic IPs
** EC2 instances
* Generate Ansible inventory

=== Step 3 — Deploy Cloudera

[source,bash]
----
./clone_and_run_pvc_automation.sh
----

This will:

* Clone Ansible automation (or pull latest changes)
* Validate required files (`sshkey.pem`, license)
* Execute playbooks to:
** Configure passwordless SSH
** Install FreeIPA
** Configure DNS
** Install Cloudera Manager
** Upload license

====

* Infrastructure provisioning only
* Cloudera deployment only

* Ensure `inventory.ini` exists in the execution directory

=== OS support (Ansible)

Playbooks support **RHEL 8/9** and **Ubuntu 22.04/24.04**.

* CM server on Ubuntu: `cm_repo_source: public` or `internal` (apt mirror on `cldr-mngr`)
* CDH parcels: `-jammy` / `-noble` for Ubuntu workers; `-el8` / `-el9` for RHEL workers
* Run from Mac, RHEL, Ubuntu, or directly on a cluster node (`cldr-mngr` / `ipaserver`)

Phased deployment via `pvc_setup.sh`:

[source,bash]
----
cd ansible-playbooks
DEPLOY_PHASE=1 ./pvc_setup.sh    # prerequisites
DEPLOY_PHASE=2 ./pvc_setup.sh    # identity (FreeIPA or AD)
DEPLOY_PHASE=3 ./pvc_setup.sh    # Cloudera Manager
DEPLOY_PHASE=4 ./pvc_setup.sh    # Auto-TLS, CMS, LDAP, Kerberos, then base cluster
DEPLOY_PHASE=5 ./pvc_setup.sh    # ECS cluster only
DEPLOY_PHASE=all ./pvc_setup.sh  # full flow
----

Set `CONTROL_MODE=local` when running on a host listed in `inventory.ini`. See link:ansible-playbooks/docs/OPERATIONS_GUIDE.md[OPERATIONS_GUIDE.md] for control-node options and environment variables (`ANSIBLE_PRIVATE_KEY`, `LICENSE_FILE`, `CM_INFO_FILE`).

=== Key playbook phases

[cols="1,3", options="header"]
|===
| Phase | Playbooks

| Prerequisites
| `00`–`09` — SSH, hostname, packages, OS tuning

| FreeIPA & DNS
| `10`–`15` — IPA server/client, DNS records

| Cloudera Manager
| `20`–`26` — repo, PostgreSQL, CM install, license

| `22` Auto-TLS, `23` Kerberos/KDC, `25` LDAP

| `28_setup_cm_cms.yml` (Management Service), `31_setup_base_cluster.yml` (full CDP base stack; see `base_cluster_install_services`)

|===

WARNING: `28_setup_cm_cms.yml` deploys the *Cloudera Management Service* (Service Monitor, Host Monitor, etc.). The CDP *base cluster* is deployed separately via `31_setup_base_cluster.yml`.

=== Cleanup

The cleanup playbook requires explicit confirmation:

[source,bash]
----
cd ansible-playbooks
ansible-playbook -i inventory.ini 99_cleanup.yml \
  -e cleanup_enabled=true -e cleanup_confirm=true \
  -e cleanup_delete_base_cluster=true
----

Available toggles: `cleanup_stop_cms`, `cleanup_delete_cms`, `cleanup_delete_base_cluster`, `cleanup_delete_ecs_cluster`, `cleanup_remove_cm`, `cleanup_remove_postgres_data`, `cleanup_e2e`, and more. See link:ansible-playbooks/docs/REFERENCE.md[REFERENCE.md].
